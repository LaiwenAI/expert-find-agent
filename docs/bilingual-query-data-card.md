# Bilingual query construction dataset

The local dataset is `artifacts/dataset-release/bilingual-query-construction-v1/`. It contains 1,000 complete original Chinese enterprise needs and 5,000 derived query intents with parallel Chinese/English text. Full English translations of the original needs remain pending. Parallel language views do not increase the independent-query count.

The five intent types are overview, component method, conditional transfer, evidence lookup, and constraint-focused search, with one generated slot per type and parent. Parents come only from the construction split of the new company/body/URL-grouped cohort. Validation and sealed groups were not used. Domain categories and source record hashes are retained for original queries; intent types describe generated requests rather than independently adjudicated labels.

Generation and native grounding/equivalence review use `gpt-6-luna`. All 1,000 parent jobs reached terminal records and all 5,000 slots contain generated text. The original screen retained 4,344 pairs. A separate conservative numeric postcheck retains 4,224 and downgrades 120; the final export retains all 776 unjudged pairs. There are **zero expert-fit labels**. Screened status does not establish human-verified semantic equivalence, relevance, or actual expert capability.

Version-2 numeric checking handles additional negated comparator aliases and abstains on unsupported nearby negation. Across all pairs it reports 4,400 numeric matches, 370 mismatches and 230 uncertain checks. A numeric match is insufficient for admission: the export intersects it with the previous grounding screen and never promotes a prior failure. Numeric-free pairs have no numeric evidence of equivalence. In the frozen 5,000-pair snapshot, 3,415 pairs have no detected numeric anchors in either view; 3,355 of the 4,224 retained pairs (79.4%) are in this category. Only 869 retained pairs have detected anchors in both views, and 576 have a detected comparator in each view. These are parser coverage counts, not estimates of semantic correctness; the parser can miss anchors. Run `PYTHONPATH=src python -m experiments.bilingual.audit_numeric_coverage` to reproduce the overall and intent-level counts. Source responses, the frozen original generator and its version-1 guard remain unchanged.

The construction screen has uneven coverage by intent: unjudged counts out of 1,000 are 115 component-method, 74 conditional-transfer, 279 constraint-focused, 212 evidence-lookup, and 96 overview. Five parents have no retained pairs, and 550 have all five retained. Among initially screened pairs, the later numeric guard downgraded eight mismatches and 112 uncertain cases. Thus filtering to retained pairs changes the type distribution and can hide hard constraints; report coverage by type and retain unresolved items as unknown. These counts describe the screening process, not measured error rates. Reproduce aggregate checks with `PYTHONPATH=src python -m experiments.bilingual.audit_screen_coverage` against the local frozen artifacts.

Rebuild locally after generation has completed:

## Numeric provenance diagnostic

A new diagnostic compares normalized numeric values detected in each generated view with the cited parent segments and the complete original Chinese need. It separately flags values found only elsewhere in the parent and values absent from the entire parent. This is a value-presence check, not a hallucination or grounding label: the parser can miss spelled-out numbers or confuse identifiers with quantities, and it cannot establish units, conversions, arithmetic, scope, comparators or semantic support.

Across the 5,000 pairs, 30 have at least one detected value absent from the full parent in either view; one was previously retained by the same-model screen and 29 were unjudged. English views account for 30 flagged pairs, and one Chinese view is flagged. Relative to cited segments, three Chinese and 43 English views contain a detected value absent from the cited text, including values that occur elsewhere in the parent. These are review candidates, not measured error rates. The audit leaves source records and existing statuses unchanged.

A local blind packet includes all 30 full-parent flags and 30 numeric-bearing controls matched on intent and original screening status, shuffled with a fixed seed. It shows the original need, cited segments and both generated views, but hides audit group and original status. The targeted sample is not a population probability sample and may be recognizable from source content. All 180 grounding/equivalence fields remain unjudged. The source and review packet remain local. Reproduce with `experiments.bilingual.audit_numeric_provenance` and `experiments.bilingual.export_numeric_provenance_review`; validate a reviewer copy using the existing `experiments.bilingual.check_grounding_review` command. The audit does not establish publication rights or anonymization.

## Adaptive HNSW effort diagnostic

A development-only test on the first 400 previously evaluated bilingual pairs (800 language views) uses the frozen 96,749-source vectors. It compares exact maximum-source scoring, HNSW effort floors 64 and 512, and a fixed heuristic: run floor 64 for 11 experts, then rerun at floor 512 when the score gap between ranks 10 and 11 is at most 0.002 or fewer than 11 experts are returned. The threshold was fixed before this run, but the dataset and general method were already explored. The gap does not bound unseen candidates, so the rule is not an exactness certificate.

In Slurm job 39610 on ws5, the gate escalated 404/800 views. Mean cached retrieval time was 1.15 ms for the gate and 1.67 ms for fixed floor 512; the company-group paired difference was -0.516 ms, interval [-0.564, -0.468] ms. Mean retention of the exact top ten was 97.9875% for the gate versus 99.7875% for floor 512; exact ordered expert and top-source lists matched in 674/800 versus 783/800 views. The fixed low-effort baseline retained 95.20% and matched 539/800 ordered lists. Index construction and copies took 23.02 seconds. These are one rotating-order observation per view on reused construction data, excluding query encoding, loading, index build from query timing, model inference and concurrent load. Fidelity to an exact vector ranking is not independent relevance or expert-fit accuracy. The loss in fidelity gives no reason to adopt this gate as the default.

The first run (job 39604) showed the same fidelity counts; job 39610 repeats it with the bootstrap sampling-unit label corrected to company group. The latter's protocol, results and summary were transferred from ws5 and their SHA-256 hashes matched the compute-node files. Reproduce using `experiments/cluster_adaptive_effort.sbatch` and `experiments.bilingual.adaptive_effort_diagnostic` after staging the frozen source and query vectors on the allocated node; the raw source and query data remain local/private.

A follow-up calibrates nine fixed gap thresholds and the direct floor-512 policy on the first 400 pairs, requiring at least 99.5% mean exact-top-ten retention and choosing the fastest measured/simulated eligible policy. It then checks the selected policy on the other 600 pairs. All 1,000 company groups are distinct, but these construction queries and their previous retrieval results were already explored, so the later pairs are not a sealed test. The threshold and target are engineering choices, not relevance labels or guarantees.

Direct floor 512 was the fastest eligible calibration policy; thresholds that met the target incurred an extra low-effort pass. On the 600 later pairs, direct floor 512 retained 99.8167% of exact top-ten entries and matched the exact ordered expert/top-source lists for 1,179 of 1,200 views. The actual replay returned the same results as the earlier baseline pass on all 1,200 views. Its measured time differed from the baseline pass even though it ran the **same algorithm**; that difference is timing drift, not an algorithmic speedup or a valid causal comparison. No adaptive gate was selected. Slurm job 39616 completed on ws5; protocol, calibration, results and summary hashes matched after transfer. `experiments.bilingual.audit_calibrated_effort` independently recomputes selection and fidelity accounting. Query encoding, initialization, index construction and model reasoning are excluded from query timing; no industrial relevance or end-to-end improvement follows.

## Shared vector snapshot for exact reference

`ExactOwnedVectorIndex.from_owned(owned_index)` creates an exact reference over the existing owned index's read-only vector array, while copying source/ownership containers. The caller must keep the original vector snapshot and shared graph unchanged; NumPy read-only flags do not provide a security boundary, and the method does not make concurrent mutation safe. This option preserves existing independent construction as the default and does not alter ranking semantics.

On 400 previously examined bilingual pairs, Slurm job 39632 on ws5 compared an independently allocated exact reference with a shared reference. All non-timing fields of 800 full results, including scores, experts and source evidence, matched. The ANN index's vector array plus reference vector array occupied 792,567,808 distinct array bytes with an independent reference versus 396,283,904 bytes with the shared reference: one 396,283,904-byte (approximately 378 MiB) vector allocation was avoided. These figures exclude the ANN graph's own storage, metadata, original memory-mapped file, temporary arrays, allocator overhead and process RSS.

After common graph construction, a single independent-reference construction took 0.091 seconds and a subsequent shared-reference construction took 0.025 seconds. Construction order was fixed; this is not a cold-start distribution. Mean exact-query times were 8.791 and 8.787 ms, with a paired interval spanning zero; no query-latency improvement is established. Both methods return exact scores under the same numerical execution, not independent expert-fit labels. The job's protocol, results and summary hashes matched after transfer. Reproduce with `experiments/cluster_shared_reference.sbatch` and `experiments.bilingual.shared_reference_diagnostic` using the frozen private vectors.

## Single-query GPU full-source scoring

An experimental `GpuOwnedVectorIndex` keeps the 96,749-source FP32 matrix on CUDA, scores every source for one query, transfers the score vector to the CPU, and aggregates experts and evidence there. The original full-source comparison did not use HNSW or eligibility filtering. TF32 must be disabled; the CPU reference's ownership metadata and the GPU snapshot must remain unchanged. A CUDA-compatible PyTorch installation is an optional runtime requirement, and the index is not a guarantee of bitwise equality to the CPU reduction.

Slurm job 39636 on ws5 compared single-view CPU and GPU full scoring on all 1,000 previously explored bilingual pairs, using an RTX 5090 and one CPU thread. All 2,000 expert orders and first-source orders matched; maximum absolute score difference among shared top-ten experts was 3.58e-7. This observed match is not an exactness certificate for other queries or devices. Mean CPU and GPU cached scoring times were 8.886 ms and 0.997 ms, respectively, including GPU query upload, full score download, synchronization and CPU aggregation. The company-group paired difference was -7.889 ms, interval [-7.897, -7.882] ms. Each view was timed once in alternating order; no competing-load or service-level test was performed. Initialization, source-vector creation, query encoding, agent reasoning, queueing and the shared model hardware cost are excluded.

The GPU scorer added 396,361,728 bytes of allocated device memory after initialization and reached a 430,307,328-byte PyTorch allocated peak during the run. These numbers exclude reserved memory, CUDA context and other device processes. The measured component speedup requires a dedicated GPU-resident matrix and does not establish industrial relevance, total system speed or independent accuracy. The source vectors, query vectors and results remain local. Reproduce on an allocated CUDA node with `experiments/cluster_gpu_full_score.sbatch`; Slurm job 39636 completed on ws5 and transferred protocol/results/summary hashes matched. A separate CUDA-node unit check verified basic ordering, evidence ownership, invalid inputs and TF32 rejection.

## GPU scoring for eligible expert subsets

`GpuOwnedVectorIndex.search_vector` now accepts eligible expert IDs. It gathers only the sources belonging to available candidates, scores them on the GPU and returns unknown IDs separately. Empty or entirely unavailable candidate lists return no sources.
